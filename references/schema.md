# IBD Companion schema

The private single-person SQLite database separates treatment, individual tests,
large review episodes, clinician-confirmed conclusions, and symptom comparison.
The same test fact may serve more than one context without being copied.

## User-facing hierarchy

```text
Injection
└── linked lab checkup

Review episode
├── lab checkup (may be the same row linked to an injection)
├── endoscopy checkup and report
├── CT / MRI / MRE checkup and report
├── pathology checkup and report
├── visit or assessment checkup
└── explicitly confirmed clinician assessment
```

SQLite stores this as rows and foreign-key links rather than physical folders.
`review_components` is the link that lets one `checkups` row appear inside a
review while `checkups.related_injection_id` can simultaneously link it to an
injection. `checkup_results` remain a single source of truth.

## Long-lived context

### `disease_profile`

Exactly one thin profile (`id='current'`): disease type, earliest symptom date,
optional diagnosis-checkup link, and sparse timeless notes. Current disease
status, affected locations, treatment state, symptom-baseline content, and dated
medical events do not belong here. Procedures, admissions, complications, and
other dated facts remain in their dated medical records.

## Treatment and routine monitoring

- `injections`: scheduled/completed biologic-infusion facts.
- `treatment_plans`: recurring injection cadence and optional linked lab rule.
- `treatment_plan_occurrences`: provenance for injections generated by a treatment plan; injection-monitoring labs link to the generated injection.
- `checkups`: one actual test, visit, or procedure-like record. A routine blood
  draw is one `kind='lab'` row and may link to an injection.
- `checkup_results`: atomic numeric or qualitative observations such as CRP,
  ESR, HGB, PLT, drug concentration, or antibody. Each value is stored once.
- `metric_definitions`: explicitly adopted observation types. A new database
  seeds six medicine-agnostic starter metrics: CRP, ESR, HGB, WBC, PLT, and
  albumin. Additional metrics, including drug-specific monitoring, are added
  only after explicit adoption through `metric-add`. Each definition has an
  immutable code, display name, numeric/qualitative type, optional default
  unit, and active state; the actual result retains its report-specific unit,
  reference range, and abnormal flag.

## Large review episodes

### `review_episodes`

One parent row for one diagnosis workup or large review. It stores review type,
title, due/completion timestamps, state, optional sequence number, and notes.

### `review_components`

Many-to-many-style membership from a review to its individual `checkups` rows.
Roles include lab, endoscopy, CT, MRI, MRE, pathology, visit, assessment,
diagnostic workup, and other. A lab linked to an injection can also be linked
to a review; no result row is duplicated.

### `checkup_reports`

Versioned reports for report-oriented tests. A current report may preserve:

- report type and timestamp;
- source organization;
- findings, impression, and original wording;
- a private attachment reference rather than embedding a file in Git.

A correction supersedes the prior version without deleting it.

### `review_plans`, `review_plan_occurrences`, `review_reminders`

Calendar-month review scheduling. Multiple plans can represent phases, for
example a bounded six-month first-year phase and a later annual phase. Calendar
months are used instead of 182/365-day approximations. Generation creates only
review parents; actual component tests are linked when explicitly planned or
recorded. When a plan's due date coincides with exactly one existing, unlinked
review (by its planned, current, or completed local date), generation records
that review as the plan occurrence rather than making a duplicate. Ambiguous
matches stop for explicit resolution.

There is no parallel `followup` plan layer. Multi-test surveillance uses
`review_plans → review_episodes → review_components`; a one-off standalone
visit or test is a direct `checkups` record. A bounded first-year review plan
never creates or activates an annual plan automatically.

## Confirmed conclusions

`checkup_assessments` remains versioned and tied to a completed checkup. In a
large review, the assessment-bearing visit/checkup is linked as a review
component. Metrics and symptoms never create an assessment automatically.

## Symptom tracking and baseline

- `symptom_logs`: append-only symptom facts with supersession.
- `factor_terms`, `factor_logs`: normalized possible factors and exposures.
- `symptom_baselines`: draft, candidate, confirmed, and historical versions.

Daily summaries are calculated from the active raw logs rather than stored as a
second medical record. They report the latest stool state, maximum/latest pain
and bloating scores, any blood/urgency/night stool, and maximum/latest
temperature. Stool total remains the latest active `day_total` plus only later
`increment` rows.

Only explicit confirmation enables a symptom baseline. It is personal usual
state, not clinician-confirmed disease activity.

## Summaries

- `current-summary`: profile, diagnosis link, latest confirmed assessment,
  latest completed review, active treatment plans, active review plans, and
  confirmed baseline.
- `overview`: adds review episodes, generated treatment occurrences, and
  pending baseline proposals.
- `review-detail`: one review parent with its component checks, current reports,
  results, and confirmed assessments.
